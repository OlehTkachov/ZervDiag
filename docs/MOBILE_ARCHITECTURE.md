# ZervDiag — мобильная архитектура

## Основной принцип

Мобильное приложение не должно повторять тяжёлую настольную часть.
На телефоне не запускаются:

- полная индексация OneDrive;
- OCR больших PDF/JPG/TIFF;
- массовая гидрация/дегидрация файлов;
- пересборка всей базы документации.

Телефон — лёгкий клиент поиска и помощника.

## Первый запуск

На первом запуске мобильный ZervDiag предлагает два режима:

### 1. Восстановить базу

Вопрос пользователю:

> У вас есть резервная копия базы ZervDiag?

Если да:

1. Пользователь выбирает portable backup.
2. Приложение читает `manifest.json`.
3. Проверяет формат и версию схемы.
4. Копирует `zervdiag.db` в private storage приложения.
5. Открывает базу локально без индексации.
6. Поиск по уже извлечённому тексту доступен сразу.

Это не копия всей технической библиотеки: PDF/JPG/DOC не помещаются в backup,
если пользователь явно не создаёт архив документов. Поэтому размер мобильной
базы определяется главным образом SQLite-текстом и индексами, а не исходными
файлами.

### 2. Lite

Если резервной копии нет:

- локальная большая база не создаётся;
- доступны интернет-поиск и настройки;
- позже можно подключить удалённый desktop/server ZervDiag;
- после появления backup его можно импортировать без переустановки.

## Почему не использовать desktop DB как есть

Текущая база содержит абсолютные Windows-пути:

`D:\\OneDrive - ...\\Service ...\\manual.pdf`

На Android такой путь не открывается. Поэтому portable backup должен иметь
manifest с корнем библиотеки, а дальнейшая мобильная схема должна уметь
показывать файл как источник даже без физического доступа к исходному PDF.

Для открытия оригинала в будущем нужны один или оба механизма:

1. относительный путь внутри библиотеки;
2. cloud/document URL (например, OneDrive share/reference), если он доступен.

## Portable backup

Предлагаемый контейнер:

```text
my_zervdiag_backup.zervdiag-backup
├── manifest.json
└── zervdiag.db
```

`manifest.json`:

```json
{
  "format": "zervdiag-portable",
  "backup_version": 1,
  "database_schema": 13,
  "created_utc": "...",
  "app_version": "...",
  "language": "ru",
  "current_root": "D:\\OneDrive - ...",
  "database_filename": "zervdiag.db"
}
```

Контракт уже описан в `mobile/backup_contract.py`.

## Нагрузка на телефон

При восстановленной базе телефон хранит SQLite и выполняет поиск по ней.
Он не выполняет OCR и не скачивает 10+ тысяч документов.

Чтобы поиск оставался быстрым и экономным по батарее, мобильная версия должна:

- открывать БД локально;
- использовать подготовленные индексы;
- ограничивать количество возвращаемых строк;
- не сканировать исходные файлы;
- не выполнять фоновые задачи без необходимости.

Если полный `content` окажется слишком большим для конкретного телефона,
можно добавить экспорт `mobile snapshot`, где хранятся только метаданные,
нормализованные технические коды и релевантные chunks.

## ИИ на телефоне

Не запускать большую LLM непосредственно на телефоне по умолчанию.

Рекомендуемые режимы:

1. **Cloud AI** — телефон локально находит 5–8 фрагментов и отправляет только
   их и вопрос облачной модели.
2. **Desktop AI** — телефон отправляет вопрос настольному ZervDiag, а тот
   делает retrieval/LLM и возвращает ответ.
3. **Local mobile AI** — только опционально для мощных устройств и маленькой
   модели; это не базовый сценарий.

Так обычный телефон остаётся лёгким клиентом.

## Безопасность

Мобильная БД должна храниться в private app storage. При импорте backup:

- проверять manifest;
- не выполнять SQL/код из manifest;
- открывать SQLite только после проверки ожидаемых таблиц;
- не хранить API-ключи внутри backup;
- не включать пользовательские ключи и пароли в `zervdiag.db`.
