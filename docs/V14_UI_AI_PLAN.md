# ZervDiag V14 — UI и основа ИИ-помощника

## Цель

V14 не меняет стабильный поисковый движок V13 и не меняет OCR-пайплайн.
Это отдельный слой интерфейса и подготовка к будущему помощнику диагноста.

## 1. Поиск и Enter

`QLineEdit.returnPressed` уже был подключён в V13. Проблема состояла в том,
что `perform_search()` молча игнорировал новый запуск, пока предыдущий
`SearchWorker` ещё работал.

V14:
- повторное нажатие Enter на текущем запросе показывает, что поиск идёт;
- новый запрос во время текущего поиска ставится следующим;
- кнопка «Найти» назначается default-button;
- один механизм используется и для Enter, и для обеих кнопок поиска.

## 2. Нулевой результат

Если локальный поиск вернул 0:
- в строке состояния остаётся явное сообщение;
- появляется отдельный диалог «Документ не найден»;
- варианты: «Изменить запрос», «Искать в интернете», «Закрыть».

Интернет-поиск на первом этапе просто открывает готовый запрос в системном
браузере. ZervDiag не получает содержимое страниц и не требует API-ключей.

## 3. Понятное название OCR

Пользовательская кнопка называется:

`Распознать сканы (N)`

Подсказка объясняет, что текст извлекается из PDF-сканов и изображений,
после чего эти документы участвуют в поиске.

Внутреннее техническое название OCR в коде пока сохраняется, чтобы не
затрагивать рабочий V13 pipeline.

## 4. Старт приложения

Приложение открывается через `showMaximized()`, а не через настоящий
безрамочный full-screen. Поэтому оно занимает рабочий экран, но сохраняет
обычные кнопки Windows и панель задач.

## 5. Как должен работать ИИ

ИИ не заменяет поиск ZervDiag.

Поток:

1. Пользователь задаёт технический вопрос.
2. Query planner выделяет модель, код ошибки и ключевые понятия.
3. Стабильный локальный поиск выбирает релевантные документы.
4. Retrieval-слой читает только уже индексированный текст из SQLite.
5. Из документов выбираются небольшие релевантные фрагменты.
6. Только эти фрагменты и вопрос передаются LLM.
7. Ответ обязан ссылаться на локальные источники `[S1]`, `[S2]`.
8. Если данных недостаточно, помощник должен это сказать.

В V14 подготовлены:
- `assistant.context.retrieve_local_context()`;
- `assistant.prompt.build_grounded_prompt()`.

Они ничего не отправляют в сеть.

## 6. Облачный и локальный ИИ

Следующий слой должен иметь единый provider interface.

Облачный режим:
- наружу отправляются только несколько найденных фрагментов;
- вся библиотека целиком не загружается;
- API-ключ хранится отдельно от БД и репозитория.

Локальный режим:
- использует тот же retrieval и prompt;
- меняется только provider;
- документация не покидает компьютер.

## 7. Будущая таблица chunks

Пока `files.content` хранит текст документа целиком. Для полноценного
помощника лучше позже добавить отдельную таблицу, например:

```sql
document_chunks(
    id INTEGER PRIMARY KEY,
    file_id INTEGER,
    page_number INTEGER,
    chunk_index INTEGER,
    text TEXT,
    FOREIGN KEY(file_id) REFERENCES files(id)
)
```

Тогда источники можно будет показывать как:

`Руководство.pdf — стр. 47`

а не только как имя файла.

Миграцию chunks не следует делать до завершения текущего OCR и проверки
качества извлечённого текста.

## 8. Интернет внутри помощника

Развивать по этапам:

### Этап A
Если локально 0 — предложить открыть обычный поиск в браузере.

### Этап B
Добавить кнопку «Дополнить поиском в интернете» даже при локальных
результатах.

### Этап C
Подключить отдельный web-retrieval provider для ИИ.

В интерфейсе источники всегда должны быть разделены:
- «Локальная база»;
- «Интернет».

Нельзя смешивать их без указания происхождения.
