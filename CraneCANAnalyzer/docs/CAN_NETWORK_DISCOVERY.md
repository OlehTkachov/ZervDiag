# CraneCAN 0.7 — Сеть / узлы

## Назначение

Вкладка `Сеть / узлы` выполняет только пассивный анализ уже принятых CAN-кадров. CraneCAN не отправляет J1939 Request, Address Claim, CANopen NMT/SDO/PDO и не опрашивает контроллеры.

Карта является логической картой обмена. Она не является схемой физической разводки кабеля, ответвлений и терминаторов.

## Быстрый порядок работы

1. Откройте PCAN-View TRC либо запустите Live/Replay в LISTEN ONLY.
2. Откройте вкладку `Сеть / узлы`.
3. Нажмите `Анализировать сеть`.
4. Проверьте оценку протокола и confidence.
5. Просмотрите таблицы `Узлы`, `Потоки`, `Периодические ID`, `События`.
6. При необходимости сохраните `.cannetwork`.
7. Для исправной и неисправной машины/состояния сохраните два снимка и используйте `GOOD / FAULT…`.
8. Кнопка `Добавить сеть в профиль` переносит автоматические наблюдения в Machine Profile. Документированные и подтверждённые пользователем данные имеют приоритет и не перезаписываются автоматической оценкой.

## Оценка протокола

CraneCAN различает:

- `ClassicalCanGeneric` — протокол верхнего уровня не подтверждён;
- `J1939Likely` — есть достаточные признаки J1939;
- `CanopenLikely` — есть достаточные признаки CANopen;
- `MixedOrGateway` — одновременно наблюдаются сильные признаки нескольких протоколов;
- `Unknown` — данных недостаточно.

Сам факт того, что 29-битный CAN ID можно математически разложить на PGN/SA, не считается доказательством J1939.

## J1939

При достаточной уверенности отображаются:

- Source Address (SA);
- Destination Address (DA) для PDU1;
- PGN;
- логические направления SA -> DA и PDU2 broadcast;
- Address Claim PGN 0xEE00;
- 64-bit NAME и его поля;
- конфликт нескольких NAME на одном SA;
- Address Cannot Claim (SA 0xFE);
- периодические сообщения и состояние узла.

При слабых доказательствах Extended-трафик показывается как `GenericExtended`: группировка по младшему байту ID является только подсказкой и не объявляет этот байт настоящим J1939 Source Address.

## CANopen

Сильными пассивными признаками считаются повторяющиеся Heartbeat/Boot-up и согласованный набор CANopen communication objects.

Для вероятного узла отображаются:

- Node-ID;
- последнее наблюдаемое NMT state;
- период Heartbeat;
- Boot-up;
- EMCY;
- наблюдаемые COB-ID;
- health/confidence/evidence.

Одиночное попадание CAN ID в стандартный диапазон PDO/SDO не считается доказательством CANopen.

## Node Health

CraneCAN обучается периодичности сообщений по медианному периоду и устойчивой группе интервалов. Редкий большой dropout не должен разрушать саму модель периодического потока.

Сетевые события включают:

- heartbeat lost / returned;
- periodic message lost / returned;
- node appeared;
- CANopen Boot-up и изменение NMT state;
- J1939 Address Claim/conflict/cannot-claim;
- появление логического SA -> DA потока.

Событийный CAN ID с нерегулярными интервалами не должен автоматически считаться пропавшим узлом.

## Снимок `.cannetwork`

Содержит:

- окно захвата и источник;
- bitrate, если известен;
- оценку протокола и evidence;
- узлы;
- логические потоки;
- периодические потоки;
- сетевые события.

`GOOD / FAULT…` показывает появившиеся/пропавшие узлы и потоки, изменение state/identity и существенное изменение периода.

## Сеть incident

`Сеть incident…` открывает сохранённый `.canincident` и пассивно сравнивает сеть до marker и после marker. Отдельно отображается временная последовательность сетевых событий относительно отметки.

Результат является наблюдаемой корреляцией. Исчезновение узла или потока около marker является диагностической уликой, но не автоматическим доказательством причины неисправности.

## Безопасность

В CraneCAN 0.7 этот функционал receive-only. Любая будущая активная диагностика J1939/CANopen должна быть отдельным bench-only режимом и не входит в текущую реализацию.
