# CraneCAN — импорт и проверка переносимого Project Package

## Назначение

`Импорт ZIP…` открывает переносимый CraneCAN package без ручной распаковки. Импорт считается успешным только после проверки структуры ZIP, внутреннего `CraneCAN.package-manifest.json`, содержимого `.canproject`, SHA-256 всех зарегистрированных resources и Project Integrity уже распакованной копии.

Импорт не выполняет CAN I/O и не добавляет передачу CAN. Это полностью офлайн-операция с файлами.

## Последовательность

1. Инженер выбирает ZIP package.
2. Выбирает родительскую папку для импорта.
3. CraneCAN создаёт имя новой папки из имени ZIP.
4. Если такая папка уже существует, импорт останавливается. Существующие материалы не перезаписываются.
5. ZIP сначала анализируется без публикации файлов проекта.
6. Допускается ровно один `.canproject` и ровно один `CraneCAN.package-manifest.json`, оба в корне архива.
7. Внутренний SHA-256 manifest читается и валидируется.
8. Корневой `.canproject` извлекается во временную папку, и его фактические длина/SHA-256 сравниваются с записанными при экспорте **до загрузки JSON проекта**.
9. Список fingerprints во внутреннем manifest должен точно совпадать с `.canproject` + зарегистрированные resources.
10. Состав файлов ZIP должен точно совпадать с `.canproject` + зарегистрированные resources + внутренний SHA-256 manifest. Лишние и отсутствующие файлы блокируют импорт.
11. Остальные resources извлекаются в приватную временную папку. Каждый payload entry хешируется SHA-256 во время распаковки и сравнивается с записанным hash/размером.
12. На временной копии выполняется Project Integrity.
13. Только после успешных проверок временная папка атомарно переименовывается в конечную папку проекта.
14. Импортированный `.canproject` сразу открывается в CraneCAN.

## Внутренний SHA-256 manifest

Текущая версия importer требует файл:

`CraneCAN.package-manifest.json`

Он содержит:

- schema version;
- идентификатор формата `CraneCAN.ProjectPackage`;
- `projectId`;
- имя корневого `.canproject`;
- относительный путь, длину и SHA-256 каждого payload-файла.

Legacy ZIP, созданный старой версией CraneCAN без внутреннего SHA-256 manifest,
не импортируется в verified-режиме. Его нужно открыть/восстановить исходным
способом и заново выполнить `Экспорт ZIP…` текущей версией.

## Защита путей

Импортер не использует слепой `ExtractToDirectory` для недоверенного архива. Каждый путь нормализуется и проверяется до создания файла.

Блокируются:

- `../` и `.` сегменты;
- абсолютные пути;
- drive-qualified пути (`C:` и аналогичные);
- пустые сегменты и NUL;
- Windows ADS через `:`;
- недопустимые Windows-символы;
- имена, заканчивающиеся точкой или пробелом;
- зарезервированные Windows device names (`CON`, `NUL`, `COM1`, `LPT1` и т. п.);
- symbolic links в ZIP;
- одинаковые пути с различием только в регистре;
- конфликт, когда один путь одновременно используется как файл и каталог.

## Ограничения размера

Для защиты от явно повреждённых/враждебных архивов действуют высокие технические пределы, не мешающие обычным большим CAN-трассам:

- до 20 000 файлов;
- до 128 GiB на один файл;
- до 256 GiB суммарного распакованного объёма;
- до 16 MiB для внутреннего SHA-256 manifest.

Перед распаковкой CraneCAN по возможности проверяет доступное свободное место на целевом диске.

## Проверка SHA-256

После выбора ZIP CraneCAN вычисляет SHA-256 самого архива. Этот SHA-256 выводится после успешного импорта и может быть сравнен с SHA-256, который был показан при `Экспорт ZIP…` на исходном компьютере.

Дополнительно importer использует **внутренний hash, записанный во время экспорта**, а не просто повторно считает hash текущего entry. Поэтому изменение байтов отдельного `.trc`, `.canproject`, `.canincident`, `.craneprofile`, отчёта и т. д. после упаковки приводит к `SHA-256 mismatch` и package не публикуется.

SHA-256 внутреннего `CraneCAN.package-manifest.json` также выводится после экспорта и импорта.

## Граница доверия

Внутренний SHA-256 manifest обеспечивает контроль целостности, но не является цифровой подписью. Если злоумышленник способен заменить одновременно payload и сам hash-manifest, он может создать другой внутренне согласованный ZIP.

Для доказательства происхождения/авторства потребуется отдельная будущая функция цифровой подписи с доверенным ключом. До этого для повышенного контроля можно сравнивать SHA-256 всего ZIP по независимому доверенному каналу.

## Строгое соответствие manifest

Package должен содержать только:

- один корневой `.canproject`;
- один корневой `CraneCAN.package-manifest.json`;
- resources, перечисленные в этом `.canproject`.

Незарегистрированные файлы не принимаются. Зарегистрированный, но отсутствующий resource также блокирует импорт. Внутренний hash-manifest обязан содержать fingerprint каждого `.canproject`/resource и не может содержать лишние fingerprints.

Persistent TRC bindings сохраняются через Resource ID. После переноса папки они продолжают указывать на соответствующие Trace resources при условии успешного Project Integrity.

## Поведение при ошибке

До завершения всех проверок конечная папка проекта не публикуется. При ошибке временная папка удаляется по best-effort правилу. Существующие каталоги и файлы пользователя не удаляются и не перезаписываются.

## Полевая рекомендация

Для передачи проекта между компьютерами:

1. На исходном ПК выполнить `Целостность…`.
2. Выполнить `Экспорт ZIP…` и сохранить показанный SHA-256 ZIP; при необходимости также SHA-256 внутреннего manifest.
3. Передать ZIP и SHA-256 по независимому/доверенному каналу, если требуется усиленный контроль передачи.
4. На целевом ПК выполнить `Импорт ZIP…`.
5. Убедиться, что importer не сообщил ни одного hash mismatch и Project Integrity прошёл.
6. При необходимости сравнить SHA-256 всего ZIP с исходным значением.
7. Перед работой на машине снова выполнить `Целостность…`.

CraneCAN остаётся receive-only/listen-only в CAN-части; импорт package не передаёт CAN-сообщений.
