# CraneCAN — Portable Project Package

## Назначение

`Project Package` создаёт проверенный переносимый ZIP-архив из текущего
`*.canproject`.

В архив попадают только:

- сам `*.canproject`;
- resources, зарегистрированные в manifest проекта;
- служебный `CraneCAN.package-manifest.json` с SHA-256 и размером каждого payload-файла.

Случайные файлы, лежащие рядом в папке машины, в package не попадают.

## Зачем это нужно

Рабочий проект может содержать Machine Profile, Guided Experiments, TRC/CSV,
incident, snapshots, отчёты и документацию. Для переноса на другой компьютер
недостаточно просто скопировать один `*.canproject`: все связанные resources
должны сохранять относительную структуру каталогов и TRC dependencies должны
оставаться однозначными.

Экспорт выполняет эту работу как одну проверяемую операцию.

## Порядок экспорта

Кнопка `Экспорт ZIP…` появляется рядом с `Целостность…`.

Перед публикацией ZIP CraneCAN:

1. выполняет `Project Integrity` исходного проекта;
2. останавливает экспорт при любом `ERROR` или `WARNING`;
3. создаёт временную staged-копию только из зарегистрированных resources;
4. сохраняет в staged-копию текущий manifest проекта с теми же Resource ID,
   active-resource ID и persistent TRC bindings;
5. повторно выполняет `Project Integrity` уже на staged-копии;
6. вычисляет SHA-256 и точный размер каждого staged payload-файла;
7. создаёт `CraneCAN.package-manifest.json`, в котором фиксируются fingerprints
   корневого `*.canproject` и всех зарегистрированных resources;
8. создаёт ZIP;
9. открывает созданный ZIP и проверяет каждый file entry:
   - нет лишних незарегистрированных файлов;
   - нет пропавших ожидаемых файлов;
   - размер совпадает;
   - SHA-256 содержимого entry совпадает со staged-файлом;
   - внутренний SHA-256 manifest также побайтно совпадает со staged-копией;
10. вычисляет SHA-256 готового ZIP;
11. только после успешной проверки публикует архив по выбранному пути.

Если любой шаг завершается ошибкой, временный package удаляется и
не публикуется как готовый результат.

## Внутренний SHA-256 manifest

`CraneCAN.package-manifest.json` имеет собственную schema и содержит:

- идентификатор формата `CraneCAN.ProjectPackage`;
- `projectId`;
- имя корневого `*.canproject`;
- для каждого payload-файла: относительный package path, длину в байтах и SHA-256.

Внутренний manifest намеренно не хеширует сам себя: иначе возникла бы рекурсивная
зависимость. SHA-256 самого manifest показывается отдельно после экспорта, а
SHA-256 всего ZIP покрывает архив целиком.

Этот механизм обнаруживает изменение отдельного файла после упаковки. Он не
является цифровой подписью: тот, кто может заменить одновременно payload и
внутренний manifest, может сформировать другой внутренне согласованный package.

## Строгое правило целостности

Portable package создаётся только для проекта без ошибок **и без
предупреждений**.

Например, экспорт блокируется, если:

- зарегистрированный resource отсутствует;
- active resource отсутствует;
- persistent binding указывает на пропавший Trace;
- Guided Experiment не читается;
- binding устарел после изменения repeat/role;
- TRC dependency не найдена;
- dependency неоднозначна;
- dependency существует только вне папки проекта;
- TRC существует внутри папки, но не зарегистрирован как Trace resource.

Это намеренно строже обычного открытия проекта: ZIP с частично отсутствующими
материалами нельзя считать переносимой контрольной копией.

## Persistent TRC bindings

Если в проекте несколько файлов с одинаковым именем, например:

```text
traces/good/capture.trc
traces/fault/capture.trc
```

сначала задайте `TRC привязки…` для соответствующего
`REFERENCE / ACTION / RETURN`.

В package сохраняются Resource ID и binding, поэтому после распаковки в другой
каталог или на другой компьютер CraneCAN продолжает использовать выбранный
Trace resource и не угадывает по имени файла.

## Что не меняется

Экспорт не изменяет исходные:

- `*.canproject`;
- `*.craneprofile`;
- `*.canexperiment`;
- `*.trc` / `*.csv`;
- `*.canincident`;
- `*.cansnapshot`;
- отчёты и документы.

Текущий объект проекта сериализуется в отдельный manifest внутри staged package.
Исходный manifest на диске не переписывается.

## Защита от перезаписи

Exporter не позволяет сохранить ZIP поверх:

- исходного `*.canproject`;
- любого зарегистрированного project resource.

Существующий ZIP заменяется только после явного подтверждения в диалоге
сохранения и только после того, как новая временная копия полностью прошла
проверку.

## Проверка после получения архива

После распаковки package ожидается структура вида:

```text
SOOSAN_JK1200A/
  SOOSAN_JK1200A.canproject
  CraneCAN.package-manifest.json
  profiles/
    JK1200A.craneprofile
  experiments/
    TELESCOPE_OUT.canexperiment
  traces/
    ...
  reports/
    ...
```

Рекомендуемый путь — использовать `Импорт ZIP…`: текущий importer сначала
сверит каждый payload-файл с внутренним SHA-256 manifest и только после этого
опубликует проект. При ручной распаковке можно открыть `*.canproject`, но такая
операция сама по себе не выполняет package hash verification.

## Контрольные суммы

После экспорта CraneCAN показывает две контрольные суммы:

- SHA-256 всего ZIP — для проверки полного файла архива при передаче/хранении;
- SHA-256 `CraneCAN.package-manifest.json` — fingerprint таблицы внутренних hash.

При обычном `Импорт ZIP…` дополнительно сверяется записанный при экспорте SHA-256
каждого `*.canproject` и resource.

## Производительность

Копирование и SHA-256 выполняются потоково. Большие TRC не загружаются целиком в
память.

Во время создания package исходные resources открываются только для чтения.
Если файл в этот момент открыт процессом на запись несовместимым способом,
экспорт останавливается вместо создания потенциально непоследовательной копии.

## Безопасность CAN

Project Package работает только с сохранёнными файлами.

Он:

- не открывает CAN-канал;
- не вызывает PCAN transmit/write;
- не меняет LISTEN ONLY архитектуру;
- не передаёт никаких кадров в сеть крана.
